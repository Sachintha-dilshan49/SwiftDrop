AI Assistant — Design & Architecture

A chatbot for SwiftDrop users that answers with live data through tools (track a parcel, estimate a fee, list my parcels) and with help-centre knowledge through RAG (shipping rules, prohibited items, delivery times). The same tools are exposed over MCP so external AI clients can use them. The LLM provider is configurable; Groq is the default.

port 8087lk.swiftdrop.aiSpring Boot 4.1Spring AI 2.0.2 LLM + toolsLLM + RAGMCP serverno database

Status: design only. The module is still a skeleton, and so are the services its tools call (gateway, parcel, pricing). Until they exist, tools are built and tested against the contracts in docs/architecture.md using WireMock.

2Approach and why

An LLM API on its own guesses. Each question type needs a different grounding technique, so the assistant combines them:

Question typeExampleTechnique
Live, per-user data"Where is SD-7K3Q-9P2M?" · "What does 2 kg Colombo→Kandy cost?" · "Show my parcels"Tool calling: the model asks to call a function, we run it with the user's token and return real data.
Static knowledge"What can't I send?" · "What happens if I'm not home?"RAG: retrieve relevant help-article passages and put them in the prompt.
Out of scope"Write me a poem"System prompt refuses politely and points back to SwiftDrop help.

Alternatives considered and rejected: a rule/intent bot (too rigid), a raw LLM call (hallucinates), and a hosted agent platform such as Bedrock Agents (vendor lock-in, harder to test, less to explain in the viva). See §18.

All routes need a valid JWT with one of CUSTOMER, MERCHANT, COURIER, DISPATCHER, ADMIN. Errors are RFC 7807 ProblemDetail from common.

7Tools (live data)

ToolArgumentsCalls (through gateway)Returns to the model
track_parceltrackingNo (pattern SD-XXXX-XXXX)GET /api/v1/track/{trackingNo} (public)status, last update time, history (no names or addresses)
estimate_feefromZone, toZone, weightKg, sizeGET /api/v1/pricing/estimateamount, currency (LKR)
my_parcelsstatus (optional), limit ≤ 10GET /api/v1/parcels with caller's JWTtracking no, status, created date for each
search_help_articles (MCP only)queryin-process vector storetop passages with article + section
  • Read-only. No tool writes anything.
  • Caller's token is passed to tools through Spring AI's ToolContext, not a thread-local, so it also works when streaming runs tools on another thread.
  • Tool results are trimmed to what the model needs. Personal data from parcel responses (recipient name, phone, address) is dropped before it reaches the LLM.
  • Errors become short messages the model can relay ("No parcel found with that tracking number"), never stack traces. 401/403 from downstream become "you don't have access to that".
  • At most 5 tool calls per request to stop loops.

8Knowledge base (RAG)

Ingestion (at startup)

  1. Read src/main/resources/knowledge/*.md.
  2. Split by heading, then TokenTextSplitter (~400 tokens, small overlap).
  3. Metadata on each chunk: article, section.
  4. Embed with the local ONNX model (spring-ai-transformers, all-MiniLM-L6-v2).
  5. Store in SimpleVectorStore (in memory).

Retrieval (each chat message)

  1. RetrievalAugmentationAdvisor embeds the question.
  2. Top-k = 4 passages with similarity ≥ 0.4 (measured with the real model: relevant questions score 0.45–0.66, off-topic about 0.1).
  3. Passages are added to the prompt as context.
  4. System prompt: answer help questions only from context; if none, say so and suggest support.
  5. Articles used are returned in sources.

Starting articles (written by us, no personal data)

FileCovers
shipping-rules.mdSize classes, weight limits, packaging
prohibited-items.mdWhat cannot be sent
delivery-times-and-zones.mdZones, typical delivery times (zone list itself comes from pricing)
fees-explained.mdHow the fee is calculated (weight, zone, express)
failed-delivery.mdWhat happens on FAILED, re-delivery
tracking-status-guide.mdMeaning of each status
merchant-api-faq.mdAPI keys, webhooks, signature check

Groq does not appear to host embedding models (checked Oct 2026), so embeddings are separate from the chat model. The local ONNX model needs no key and no new container; an OpenAI-compatible embedding endpoint can be configured instead.

9Model registry

Spring AI 2.0.2 has no Groq starter, but Groq exposes an OpenAI-compatible API. The registry builds one OpenAI-compatible ChatModel (and a ChatClient) per enabled entry. The same mechanism covers OpenAI, OpenRouter and a local Ollama.

swiftdrop:
  ai:
    default-model: ${AI_DEFAULT_MODEL:groq}
    models:
      groq:
        enabled: true
        base-url: ${AI_GROQ_BASE_URL:https://api.groq.com/openai/v1}
        api-key: ${AI_GROQ_API_KEY}                # secret, no default
        model: ${AI_GROQ_MODEL:openai/gpt-oss-120b}   # llama-3.3-70b-versatile was retired in Aug 2026
        temperature: 0.2
      openai:
        enabled: ${AI_OPENAI_ENABLED:false}
        base-url: ${AI_OPENAI_BASE_URL:https://api.openai.com}
        api-key: ${AI_OPENAI_API_KEY:}
        model: ${AI_OPENAI_MODEL:}
      ollama:
        enabled: ${AI_OLLAMA_ENABLED:false}
        base-url: ${AI_OLLAMA_BASE_URL:http://localhost:11434}
        model: ${AI_OLLAMA_MODEL:}
  • Startup fails fast if the default model is missing, disabled or has no key.
  • A request can name a model; only configured, enabled names are accepted (400 otherwise). Clients can never send a URL or raw model id.
  • Adding Anthropic or Bedrock later = one new provider type in the registry plus its starter; nothing else changes.

14Security & privacy

ConcernDecision
AuthenticationJWT verified by common's auto-configuration (JWKS from auth-service). Applies to chat endpoints and /mcp.
Authorization@PreAuthorize requires a SwiftDrop role. Data access is enforced downstream because tools forward the caller's JWT; the assistant never uses a service token for user data.
Conversation isolationMemory key is userId:conversationId; another user's conversationId simply finds nothing.
Prompt injectionRead-only tools, a narrow system prompt, tool arguments validated (tracking-number pattern, weight > 0, limit ≤ 10), tool output treated as data.
PII to the LLMTool results drop recipient name, phone and address before reaching the provider. Help articles contain no personal data.
LogsNo prompts, replies or tool payloads in logs. Log model name, tools used, latency and token counts only. PiiMasker from common as a safety net.
SecretsProvider keys from environment variables only; never returned by /models.
Abuse and costMessage max 2000 chars, memory window 20, max 5 tool calls, provider timeout; per-user rate limit on /api/v1/assistant/** in the gateway (Role 1).

18Design decisions

DecisionWhyAlternative rejected
LLM + tools + RAGTools for live data, RAG for static knowledge; each grounds a different question typeRaw LLM (hallucinates); rule bot (rigid)
Tools call the gateway with the user's JWTReuses existing auth and ownership rules; no duplicated checksService token + own checks (duplicates rules, risk of leaks)
One tool class for chat and MCPDRY; both contracts in architecture.md metSeparate MCP and chat implementations
Groq default via OpenAI-compatible clientFast, low cost, OpenAI-compatible API; no extra dependency for other compatible providersSingle hard-coded provider; AWS Bedrock as default (AWS setup, demo risk)
RAG as advisor in chat, tool over MCPAdvisor always grounds chat answers; MCP clients choose for themselvesRAG only as a tool (small models may skip it)
Local ONNX embeddingsGroq has no embeddings; no key, no container, works offlineOpenAI embeddings (second paid key) — kept as an option
In-memory SimpleVectorStoreSmall knowledge base rebuilt in seconds; fits "no database" rulepgvector (new DB for this service, needs an ADR)
In-memory chat memoryNo database; conversations are short-livedRedis/JDBC memory (more infrastructure)
SSE for streamingSame technique already used for tracking; works through gateway and ingressWebSockets (two-way not needed)

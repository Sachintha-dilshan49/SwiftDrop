SwiftDrop system architecture

Microservices behind a single API gateway. Services talk synchronously over REST when they need an answer now, and publish parcel status events to RabbitMQ when other parts of the system only need to react. Every service owns its own database.

React + ViteJava 21 · Spring Boot 3Spring Cloud GatewayPostgreSQL 16RabbitMQRedisMinIODocker · Kubernetes · HelmGitHub Actions

Scroll sideways on a phone. Short arrows between services: parcel calls pricing for the fee, dispatch calls parcel to change status, merchant calls parcel to create an order.

Layers

LayerWhat lives there
PresentationReact SPA for all roles, mobile-first public tracking page. Talks only to the gateway.
EdgeIngress (Kubernetes) and api-gateway: auth check, routing, rate limits, CORS.
Business logicSeven Spring Boot services, each layered as Controller → Service → Repository, with DTO validation at the controller.
IntegrationRabbitMQ topic exchange, notification consumer, webhook sender with retry.
DataPostgreSQL (database per service), Redis, MinIO object storage.

Integration patterns

  • request/reply Gateway to services, parcel to pricing, merchant to parcel, dispatch to parcel. Used when the caller needs the answer before it can respond.
  • publish/subscribe Parcel publishes one event per status change; four queues react independently, so adding a consumer never touches parcel-service.
  • message broker + DLX Durable queues and dead-letter retry give at-least-once delivery for notifications and webhooks.
  • transactional outbox Event is written in the same DB transaction as the status change, then relayed to RabbitMQ, so no event is lost if the broker is down.
  • webhook Outbound HTTP callback to merchants, signed with HMAC-SHA256, retried with backoff.
  • server-sent events One-way live stream from parcel-service to browsers through the gateway.

Key flows

1. Customer creates a delivery

  1. SPA calls GET /pricing/estimate and shows the fee.
  2. Customer confirms; SPA sends POST /parcels with the JWT.
  3. Gateway verifies the token and routes to parcel-service.
  4. Parcel-service re-checks the fee with pricing, saves the parcel as CREATED with a history row and an outbox row in one transaction.
  5. Outbox relay publishes parcel.status.created; API returns 201 with the tracking number.

2. Merchant creates an order through the API

  1. Store server sends POST /merchant-api/orders with X-API-Key.
  2. Gateway applies the per-key rate limit; merchant-service checks the key hash and that the merchant is approved.
  3. Merchant-service calls parcel-service to create the parcel with its merchantId.
  4. CREATED event flows to webhook.q; the webhook sender POSTs to the merchant URL.

3. Courier updates status

  1. Courier sends POST /courier/deliveries/{id}/status with a note or photo.
  2. Dispatch checks the delivery is assigned to this courier (403 otherwise) and stores the photo in MinIO.
  3. Dispatch calls parcel-service; parcel validates the transition (State pattern) and saves history and outbox.
  4. One event fans out: email/SMS, merchant webhook, report counters, and an SSE push to every open tracking page.

4. Login with Google

  1. SPA redirects to /oauth2/authorization/google on auth-service.
  2. User signs in at Google; Google redirects back with an authorization code.
  3. Auth-service exchanges the code, finds or creates the user as CUSTOMER, and issues our own JWT and refresh token.
  4. SPA receives a one-time code on /auth/callback and swaps it for the tokens.

Status event contract

Routing key parcel.status.<status>. Contains IDs only, no addresses or phone numbers; consumers look up contact details through internal APIs.

{
  "eventId": "8f2c1e0a-…",
  "type": "ParcelStatusChanged",
  "version": 1,
  "occurredAt": "2026-10-21T09:15:00Z",
  "parcelId": "c41d…",
  "trackingNo": "SD-7K3Q-9P2M",
  "customerId": "a9e0…",
  "merchantId": "5b17…",      // null for customer bookings
  "courierId": "e3f8…",       // null before assignment
  "fromStatus": "IN_TRANSIT",
  "toStatus": "OUT_FOR_DELIVERY",
  "note": "Left Kandy hub",
  "failureReason": null
}

Status machine

CREATED → PICKED_UP → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED or FAILED. Any other transition returns 409.

Consumers

  • notification.q: email on every status, SMS on OUT_FOR_DELIVERY, DELIVERED, FAILED.
  • webhook.q: only events with a merchantId.
  • dispatch.q: daily counters for reports.
  • tracking.q: SSE push to open tracking pages.

Consumers are idempotent: eventId is stored, and duplicates are skipped.

Security

  • Passwords hashed with BCrypt; Google users have no password.
  • Access token: JWT RS256, 15 minutes. Refresh token: 7 days, rotated, stored hashed.
  • Gateway and every service verify tokens with the public key from JWKS, so no shared secret is copied around.
  • Roles: CUSTOMER, MERCHANT, COURIER, DISPATCHER, ADMIN, enforced with @PreAuthorize.
  • Ownership checks in services: a courier sees only their assignments, a customer only their parcels, a merchant only their orders.
  • Internal endpoints (/internal/**) are not exposed by the gateway.
  • Merchant API keys shown once, stored as SHA-256 hashes, rate-limited per key.
  • Bean Validation on every request DTO; one shared handler returns RFC 7807 ProblemDetail with no stack traces or personal data.
  • Logback masking for phone numbers, emails and addresses.
  • All secrets from environment variables (.env locally, Kubernetes Secrets in the cluster).
